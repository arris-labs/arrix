## Goal

The north-star demo runs (`SEED.md` §7). The world gains a `commands`
export on all three tiers. A command is declared like a feature's form:
params, choices and inputs, with the inputs seeded from the selection and
arriving resolved. The plugin expands it into one `Group` of core commands
(ADR-0004), and the session submits that group and inverts it like any
other command. `fasteners`, first-party plugin #2, is Python and runs at
Tier 2 only. Its `fasteners.socket-head` feature builds an ISO 4762 cap
screw from one table, and its `fasteners.place` command puts a screw into
each picked hole edge. Each size is a part whose history is that feature,
and each screw is a component held by a fixed joint anchored on the hole's
edge. The command runs from a ribbon button in the app and from a request
over `arrix serve`. `gears`, `robotics` and `fasteners` are each a
project of their own in the tree. The Rust ones are Cargo workspaces on
`arrix-plugin-api` alone, tested by `arrix-plugin-test`, the Rust kit. All
three pass `arrix test` from an installed `arrix`. An ADR reviews
`arrix-plugin-api` for 0.x stability. `cargo test -p arrix-cli --test
c3_accept` then runs the demo: screws placed into the bracket's picked
holes, a URDF from `robotics` as a Tier 1 component that matches urdfdom's
reading, and the file opened with neither plugin, its fastener features
frozen with their reason, where an edit of the plate's thickness or of the
pattern's spacing still moves the holes and the screws (a width edit moves
neither: Findings 3).

## Non-goals

- Plugin document data (`PluginData`, record nodes): `fasteners` stores
  nothing of its own. A screw is a part, a feature, a component and a joint,
  all core records (ADR-0034, Consequences). The ADR-0004 groups carry
  core commands only.
- Importers, analyses, panels, context-menu entries and viewport drawables
  by plugins; a gizmo; unloading a plugin (`docs/ROADMAP.md` §C3, out).
- Screw families beyond ISO 4762, modelled threads, washers and nuts, and
  a hole's depth read to choose a length (the length is a parameter).
- The plugins' own repositories and a published `arrix-plugin-api`: the
  human's acts, after the accept (ADR-0034). In-tree projects stand in for
  them.
- A command run headless from the CLI (`arrix command …`): `arrix serve`
  and `arrix.session` reach commands, which the accept needs.
- The app's export dialog listing plugin exporters (still a backlog line).
- Tier 1 in the browser (C4's ADR).

## Design deltas

- **ADR-0038, plugin commands** (step 3), from steps 1 and 2:
  - *The spec*: `commands() -> list<command-spec>` (id `<plugin>.<name>`,
    title, the ribbon group it sits in, and `params`, `choices` and
    `inputs` reusing the feature form's specs). A command form is derived
    exactly as a create form is (`docs/UI-RENDERING.md` §Forms as built).
  - *Inputs arrive resolved, in the assembly's frame.* A command runs in a
    context: a part, or an assembly. An `edge` input picked in an assembly
    carries the component path and the persistent name (an `Anchor`'s
    shape, ADR-0029). It also carries the edge's resolved geometry: a
    circle's centre, normal and radius, or a line's points, from a recorded
    kernel call against the base generation's evaluation. A plugin reads
    a hole's size and side without its own kernel call.
  - *The snapshot during expansion*: under `document-read`, `document` may
    be called during an `expand` call against the base generation, as it
    is during an export (ADR-0037 §5 is widened). The snapshot's part
    gains its history's feature types and evaluated params, so a plugin
    finds the parts it made (Open question 2).
  - *The output*: `expand(id, context, params, choices, inputs, ids) ->
    result<command-group, diagnostic>`. A `command-group` is a label and a
    list of plugin-API command records. These are a mirror of the core
    commands a plugin may issue: `add-part` (with its features),
    `add-feature`, `add-component`, `edit-component`, `add-joint`,
    `edit-joint`, `add-material` and `assign-material`, as plain records
    whose ids are the API's `id`. Deletes are left out until a plugin needs
    them. The host translates the group into one `Command::Group` and
    refuses it whole if any record is malformed (`command.invalid`, naming
    the record). Undo is its inverse, computed by the core (ADR-0004).
  - *Ids*: a record's id is minted by its author (`docs/DATA-MODEL.md`
    §Identifiers). The host passes `ids`, a list of fresh ids, sized by
    the spec's `max-new` or by a default. Expansion is then a pure
    function of its arguments and the snapshot, which the test kit checks
    by expanding twice.
  - *Capability*: a plugin contributing commands needs `document-write`. A
    command spec from a plugin without it is refused at registration
    (`plugin.capability`).
  - *The session*: `Request::Expand { command, context, params, choices,
    inputs, base }` is answered `Expanded { group }` (or the diagnostic),
    and makes no generation. The client submits the group as an ordinary
    envelope, so a preview of it is ADR-0019's `Preview`. The fields are
    additive, so the protocol stays at version 1 (ADR-0026 §3); the schema
    golden changes (Open question 1).
  - *The app*: a plugin's commands enter the command registry as
    `<plugin>.<name>`, on the plugin's ribbon tab (`[contributes] ribbon`).
    Running one opens a command form in the property card, seeded from the
    selection as a create form is, with picks in an assembly's view
    carrying their component path. OK expands, then submits: one gesture,
    one undo entry.
- **`arrix-plugin-api`** (step 4): the `commands` export and its types in
  the WIT, a resolved `edge` with path and geometry, the snapshot part's
  features, and their Rust mirror: a `Commands` trait (as `Exporter`) and
  plain command records. `export_plugin!(features = …, exporters = …,
  commands = …)`. API: breaking, 0.7.0 → 0.8.0. The wire codec, the Python
  stubs, `wit_equality.rs`'s inventory and every manifest's `api` follow.
- **`arrix-doc`** (step 5): `Registry` holds `CommandType`s beside feature
  types and exporters. `expand` resolves inputs from an evaluation, mints
  the ids, calls the plugin, and translates and checks the group.
  `Request::Expand` is added. Nothing persists, so the schema does not
  change.
- **`arrix-plugin-host`** (steps 5, 7, 8): `register_tier0` registers
  commands; Tier 1 calls `commands.expand` in a fresh store with fuel; the
  Tier 2 wire gains `commands.*` (host to plugin), with `document.*`
  answered while an expansion runs.
- **Test kit** (step 6): `[[test.commands]]` names a fixture document, a
  command, a context, options and inputs as references. The kit expands
  twice to identical groups, then applies the group and undoes it to the
  fixture's bytes.
- **`plugins/fasteners`** (step 9): Python, Tier 2, with
  `document-read` and `document-write`. It holds the ISO 4762 table (M2 to
  M12: head diameter and height, socket size and depth, clearance holes),
  `fasteners.socket-head` (params `size`, a choice, and `length`; head,
  shank and hex socket by `extrude` and `cut`; no thread), and
  `fasteners.place`, whose inputs are a list of hole edges and whose
  params are `length` and an optional `size`. A screw's head underside is
  anchored by a fixed joint on the picked edge, its `flip` from the edge's
  resolved normal and the side step 1 establishes.
- **Out of tree** (steps 2, 11, 12): `plugins/gears` and
  `plugins/robotics` leave the root workspace's members. Each becomes a
  workspace with its own `Cargo.lock` and lints, and its `arrix-plugin-api`
  is a path dependency standing in for the published crate. The binaries'
  Tier 0 lists keep naming them, in the way step 2 finds works.
  `arrix-plugin-test` is a new crate: the kit's checks move out of
  `arrix-cli/src/plugin_test.rs`, so `arrix test` and a plugin's own
  `cargo test` run the same code. A plugin may take it as a
  dev-dependency, and that is the layer lint's one new edge. The hooks and
  CI run each plugin project, and `gate-selftest` holds the lists equal.
- **ADR-0039, `arrix-plugin-api` reviewed for 0.x stability** (step 13):
  each item of the world and its Rust mirror is kept, renamed or cut, and
  the ADR says what a 0.x minor may break from here on.

## Arris dependencies

On the pinned `arris` 0.8:

- An anchor on a circular edge: `Kernel::anchor_frame`, as
  `crates/arrix-kernel/src/anchor.rs` resolves it (the circle's normal as
  Arris orients it, at its centre). On a counterbore's top edge it points
  down the hole, copies made by a pattern included (step 1, Findings 2).
- A circular edge's radius and a line's ends, for resolved command inputs.
  They come from the same curve the anchor reads. A new recorded call in
  `arrix-kernel`, with no new Arris API.
- A screw's body: `extrude` of circles and `cut` of a hexagon, both in the
  kernel service. The hexagonal-prism fillet refusal (`docs/BACKLOG.md`)
  does not arise, since the screw has no fillet.

A finding in step 1 (the patterned hole's edge renamed by a width edit, an
anchor on one failing) becomes a fixture and a backlog line, and the step
that needs it waits.

## Open questions

- ⚠ OPEN 1 (human, by step 3): expansion as its own request
  (`Request::Expand`, then an ordinary submit) or a single request that
  expands and submits. The recommendation is two requests. The client sees
  the group before it is applied, a command form's preview is ADR-0019's
  `Preview` of it with no new machinery, and the authority applies only
  core commands.

  chosen. The recommendation is from the radius, since the demo's gesture

## Findings

Step 1 (`crates/arrix-cli/tests/probe_c3_m3.rs`, on `arris` 0.8):

1. **Names.** A counterbore's top edge is generated by the hole from the
   plate's top face and the counterbore's side:
   `edge:sweep.<plate>.end-cap/gen.<hole>[…]`. The pattern's copies are
   generated by the pattern, one index per copy: `gen.<pattern>[…/inst.
   <pattern>.1]`, then `gen.<pattern>.1[…/inst.<pattern>.2]`. Each name
   survives width, thickness and spacing edits, so no joint needs a re-bind.
2. **The side.** Arris orients each of those circles down the hole, into
   the plate (-z), for the original and the copies alike. A cylinder's end
   edge is oriented along the extrusion, out of the cylinder. A fixed
   joint left unflipped makes the two equal, which stands the cylinder on
   the plate. `flip: true` puts it in the hole with its end edge at the
   hole's top. The circle's orientation is Arris's choice, not a stated
   property, so ADR-0038 should not make a plugin read the side from it
   alone. The resolved `edge` can also carry the outward normal of the
   planar face the edge bounds (`face_frame`, outward by construction), and
   `fasteners.place` sets `flip` so the screw's axis runs against it.
3. **Width does not move the holes** in `tests/docs/bracket`. The plate
   grows away from its fixed corner, and the `Top` datum plane the hole
   sketch stands on stays put (as `c1_accept`'s criterion 4 found for the
   gear). The thickness `t` moves every hole up by the change. The
   pattern's `spacing` moves each copy by its index times the change. Each
   cylinder moves exactly (to 1e-12 m) with its hole. Step 16's edits are
   these two, changed from "width".
4. **Frozen.** Saved with its result and opened without `probe.cylinder`,
   the cylinder is `plugin.frozen.missing`. Each joint still resolves on
   the frozen body's names, at exactly the live pose, and follows the same
   edits. A `fasteners.socket-head` frozen in the accept needs nothing
   more.

Step 2 (`plugins/gears` as a workspace of its own, then reverted for step 11,
which moves both Rust plugins and the gate together):

5. **It holds.** `plugins/gears/Cargo.toml` gets `[workspace]`, its package
   fields and `[lints.rust]` written out (no `.workspace = true`), and
   `arrix-plugin-api = { path = "../../crates/arrix-plugin-api" }`, as the
   host's `tests/plugins/misbehave` already does. The root needs
   `exclude = ["plugins/gears"]` beside dropping it from `members`; without
   it cargo refuses ("multiple workspace roots found"). The root's
   `arrix-gears = { path = … }` and the binaries' Tier 0 lists stay as they
   are, and the root's `Cargo.lock` does not change.
6. **What ran green.** From the root: `cargo check --workspace
   --all-targets`, `--test tier1`, `--test tier1_parity` (Tier 0 from the
   root's lock, Tier 1 from gears' own, identical), `--test plugin_test`,
   `--test c3_m1`, `--test gears`. From either directory, by
   `--manifest-path plugins/gears/Cargo.toml` or `cd`: `cargo clippy
   --all-targets --all-features -- -D warnings` (its `clippy.toml`'s
   disallowed `f64::sin` still fires), `cargo test`, and `cargo build
   --release --target wasm32-unknown-unknown --features guest`. A Tier 1
   build of the plugin is `--manifest-path` (the misbehave fixture's way),
   not `-p`, and `guest_build.rs` runs from its own manifest directory.
7. **What the gate must add (step 11).** The root's `cargo clippy
   --workspace` and `cargo test --workspace` no longer reach the plugin, so
   the hooks and CI run clippy, test and the wasm32 `guest` build once per
   plugin by `--manifest-path`. `cargo fmt --all` at the root still covers
   it (a path dependency). `scripts/layer-lint` reads the root's `cargo
   metadata` alone and loses the plugin's edges: its gate-selftest case
   "a second arrix-* dependency in a plugin" fails, so the lint also reads
   each plugin workspace's metadata. The path rule still holds.
8. **Costs.** The plugin's own `target/` (1.1 GB after one test run) is not
   ignored by the root's `/target` pattern: `target/` goes in a
   `.gitignore`, or the hooks pass `--target-dir target/plugins/<name>`.
   Its own lock drifts from the root's on shared crates (`glam` 0.33.12
   against 0.33.10, `serde_json`, `syn`); parity still held, and an
   out-of-tree author has the same drift, so it is accepted, not pinned.
