# Plan: c2-m2

- Started: 2026-10-11
- Cycle: C2, M2 (the app); ADR-0027 splits the cycle, ADR-0029 §13
  defers the drag's preview to this milestone's ADR
- Idea: none; verbatim from the human: "/plan m2"

## Goal

The app shows, builds and moves assemblies. A tab looks at one context, a
part or an assembly (session state); an assembly's context draws each
placed component's final bodies at its world pose from the `Assembled`
events, one upload per body however many components instance it. A pick
or hover lands on an entity *of a component* (its path and the name), and
the status line says which. The tree card lists assemblies with their
components, nested, and their joints with their state; activating a part
or an assembly switches the context. From an Assembly ribbon tab the user
imports a STEP part (one gesture, one `Group`), makes an assembly, inserts
a component, and creates a fixed, revolute or prismatic joint by picking
its two anchors in a create form, OK being one `AddJoint`; an edit form
changes a joint or a component field by field, a lost anchor re-picked
from its candidates. A left drag on a joint-placed component turns or
slides it about its joint, previewed by forward kinematics on the UI
thread from the last outcome's anchor frames, and the release commits one
command. `arrix-app render` renders an assembly headless.

## Non-goals

- STEP with product structure, materials, mass properties, the cycle's
  accept against Open CASCADE: M3. STEP export stays refused
  (`kernel.export.unit`, A12).
- Editing a part in place at a component's pose: features and sketches
  are edited in the part's context, at its own origin (backlog).
- A preview of a joint's create form (it needs the anchor frames, which
  only an evaluation of the draft gives; ADR-0019's preview carries no
  `Assembled` yet): backlog.
- Deleting a component, a joint or an assembly from the app: the app
  deletes no feature either yet; undo covers a gesture. One backlog line
  for deletion from the tree, features included.
- Dragging a grounded component to a new pose, or a free drag that infers
  a joint: only a joint's value is dragged.
- A general mate solver, loops (named cycle); interference (named cycle).
- More than 1,023 visible instances (the pick id's ten body bits): a
  scene past it draws the rest unpickable, as today.
- `arrix-plugin-api`: no change. The protocol and the eval line: no
  change (the joint outcome already carries both anchor frames).

## Design deltas

- **ADR-0030, assemblies in the app** (step 1):
  1. *The context.* A tab looks at `Context::Part(PartId)` or
     `Context::Assembly(AssemblyId)`, session state. A document opens in
     its first root assembly (one no assembly contains, by id), else its
     first part, so every document without assemblies looks as it does
     today. Activating a part or an assembly in the tree switches; a form,
     sketch mode or a tree feature's activation needs (and switches to)
     its part's context. A part's context draws its final bodies at its
     origin, an assembly's draws each placed component's at its world pose
     (`assembly.unplaced` ones at identity, as FK put them).
  2. *Instanced scene* (`arrix-viewport`): a mesh per `BodyKey`, uploaded
     once, and a list of `Instance { path: Vec<ComponentId>, key, model }`
     drawn one draw each; a part's context is one instance per body with
     an empty path and the identity, so the draw and pick paths are one.
     The pick id's body bits index the visible instances; a pick resolves
     to `Hit { path, name }`; hover, selection and the form's marks are
     `(path, name)`; locate, bounds and badges are per instance.
  3. *The drag is the client's* (closes ADR-0029 §13, as ADR-0005 for a
     sketch): no kernel call is involved, so the UI thread composes FK
     from the last `JointOutcome::Ok`'s `parent` and `child` frames and a
     trial value (`arrix-doc`'s pure FK, the evaluator's own), and moves
     the child's subtree by model matrices only, nothing uploaded. The
     dragged joint is the one placing the deepest component of the picked
     path that a joint places in the context; a grounded or unplaced one
     does not drag (a hint). The trial value is clamped to the joint's
     limits.
  4. *What a release commits*: a joint whose `value` is a literal gets
     `EditJoint` with the new literal (display units); one whose value is
     a single parameter's name gets that parameter's edit (the scenario's
     `angle`), so a drag never overwrites an expression; any other
     expression refuses the drag with a hint. One gesture, one command,
     none for a release where it started.
  5. *Forms the app builds*: a joint and a component have no feature
     spec, so the app builds their `FormView` (the one renderer, ADR-0018)
     from the record: a joint's kind (choice), parent and child anchors
     (reference fields taking an axis and an optional origin face, picked
     with their path), value, offset, the two limits, flip (a choice of
     two); a component's name, what it instances (choice) and its pose
     (six quantities, grounded or not). An edit form commits one
     `EditJoint`/`EditComponent` per field; a create form is a draft until
     OK, one `AddJoint`/`AddComponent`.
  6. *Commands*: an Assembly ribbon tab, `core.assembly`, holding
     `core.import-step.create` (an open-file dialog behind a seam beside
     the save dialog; one `Group` of `AddFile`, `AddPart`, `AddFeature`,
     ADR-0029 §9), `core.assembly.create` (`AddAssembly`, then its
     context), `core.assembly.component.create` and
     `core.assembly.joint.{fixed,revolute,prismatic}`, enabled only in an
     assembly's context; a keymap context `assembly`.
- **`arrix-doc`**: the FK of ADR-0029 §4 exposed as a pure function the
  evaluator and the app share: world poses from an assembly, its nested
  outcomes, the joints' frames and values, with one value overridden.
- **`arrix-viewport`** `Scene`: meshes and instances (above); `BodyEntry`'s
  `model` moves to the instance (a pose in f64 composed with the mesh's
  origin, cast to f32 last); `PickBodies` names instances.
- **`arrix-ui`**: `TreeView.assemblies` (`TreeAssembly { id, name,
  components: Vec<TreeComponent>, joints: Vec<TreeJoint> }`, a component
  with how it is placed, grounded, by a joint, unplaced or in a loop, and
  its nested children; a joint with its kind, state and note); intents
  `TreePartActivated`, `TreeAssemblyActivated`, `TreeComponentSelected`,
  `TreeJointActivated`; `Picked`/`Hovered` carry the path (strings, so
  `arrix-ui` names no doc type).
- **`arrix-app`**: the replica's `Assembled` outcomes, the context,
  `debug_state()` gaining `context`, `instances` and the selection's
  path; `render --context <part|assembly id or name>`, the render schema
  golden refreshed (`Harness: render 1, additive`).
- **`arrix-config`**: the new commands, tab and keymap context;
  `describe` and `docs/CONFIG-CATALOG.md` regenerated; `core.import-step`
  leaves `creatable_specs`' exclusion (c2-m1 step 9) for its own command.
- **Budgets** (`docs/CONCURRENCY-WASM.md` §Budgets): a joint-drag frame
  on the accept's assembly, ≤ 16 ms on the UI thread, gated.

## Arris dependencies

None new. The app calls no kernel; the import and the anchor frames are
M1's (`io::step::read`, `Role::File`, `ops::query::face_frame`, in the
pinned `arris` 0.6).

## Acceptance

`cargo test -p arrix-app --test visual c2_m2_accept`, on
`tests/docs/assembly` with its assembly removed by a scenario-side
`DeleteAssembly` before the first frame (the app deletes nothing yet, and
rebuilding the bracket feature by feature tests nothing of M2's), then through
the app's own commands, the scenario answering the dialogs:

- Import the servo's file from `tests/fixtures/step/` as a new part (one
  gesture, one command).
- Make an assembly, insert the bracket grounded and the servo twice;
  `debug_state().instances` holds three, the servo's mesh uploaded once.
- Create a revolute joint by picking the servo's shaft face (with the
  first servo's path) and the bracket's bore face, OK: one `AddJoint`,
  the first servo lands on the bore as `tests/docs/assembly` places it
  (the same pose within 1e-9 m).
- Drag the first servo: the preview's pose equals FK at the trial value;
  the release is one command, after which the evaluated pose equals the
  preview's; the second servo, grounded, does not move and does not drag.
- A pick on the second servo selects its path; undo walks back each
  gesture, one command each, to the opened document; the gesture log's sum
  is `commands_applied`.
- `arrix-app render tests/docs/assembly --context <assembly>` writes a
  PNG and JSON whose instances match the eval line's poses.
- The whole gate (`.githooks/pre-commit`, `.githooks/pre-push`) stays
  green, the wasm build included.

## Open questions

None open. Decided by the human, 2026-10-11, both as recommended:

- One part or one assembly per tab (ADR-0030 §1), features edited only in
  a part's own context.
- A drag on a joint whose value is a single parameter edits that
  parameter (ADR-0030 §4).

Decided at planning by the agent:

- The accept starts from `tests/docs/assembly` minus its assembly, since
  the app has no deletion and rebuilding the bracket tests nothing of
  M2's; the import, assembly, components, joint and drag are all
  the app's.
- `flip` is a two-option choice in the joint form, not a new checkbox
  field kind in `FormView`.
- One plan for the milestone, as M1 was; M3 is planned when this retires.
