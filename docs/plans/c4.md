# Plan: c4

- Started: 2026-10-15
- Cycle: C4, the web; ADR-0042 details the cycle
- Idea: docs/ideas/browser-worker-cancellation.md (absorbed). On
  2026-10-15 the human chose option A, a `SharedArrayBuffer` counter, with
  the preferred answers: without cross-origin isolation, a superseded
  evaluation runs to its end with a status-line notice; the latency is gated
  at 50 ms in the headless accept. The idea's third answer ("the client
  raises; the authority and the evaluator share one worker") was revised
  at planning on the same day. The app reads `Session::request`
  synchronously at about twenty call sites, and a browser main thread cannot
  block on a worker. So the human put **the authority on the main thread
  and the evaluator alone in the worker**, and the authority bumps the
  counter after it applies a commit, as it raises the flag natively.

## Goal

`arrix-app` runs in a browser tab, served by a local page that is
cross-origin isolated. The kernel never runs on the main thread. The
authority runs there, synchronous, kernel-free and unchanged in behaviour.
The evaluator runs in one web worker, and the two exchange the same plain
data the session thread and the evaluator thread exchange natively. A
document opens from bytes, an edit evaluates in the worker, and the eval
line equals native's to the bit. A commit stops a superseded evaluation
inside its kernel call within 50 ms. It does so through a
`SharedArrayBuffer` counter that the worker's Arris poll reads, and
previews keep ADR-0019's rules. On a page without isolation the app still
works, a superseded evaluation runs to its end, and the status line says
so. Files are opened and imported from the browser's file picker, and
saves and exports are downloads. A document using a Tier 1 or Tier 2
plugin opens with those features frozen, bodies kept, and the page says
why. The risk this retires: the native evaluator and its determinism hold
on wasm32 in a worker.

## Non-goals

- Tier 1 in the browser (its own ADR) and Tier 2 (a process). There is no
  `PluginLoader`, so `LoadPlugin` and `ReloadPlugin` are
  `Rejected::NoPluginLoader` (ADR-0024).
- Shared wasm memory and threads in the browser (the idea's option B):
  nightly and `-Zbuild-std`. The toolchain stays `stable`.
- A public deployment of the page: hosting, a service-worker shim for
  hosts without headers, a domain. `scripts/web-serve` is for development
  and tests. To the backlog.
- User config files in the browser. There is no filesystem, so the page
  runs the shipped defaults (ADR-0015), and storing user config is offline
  storage (out). To the backlog.
- Offline storage beyond a download, remote mode and accounts, touch and
  mobile layouts (`docs/ROADMAP.md` §C4 Out).
- Browser budgets other than cancellation. The first coarse mesh in wasm
  is reported, not gated (it misses natively already).
- Parallel evaluation, Arris's `parallel` feature, on wasm.

## Design deltas

- **ADR-0042, C4 is the web** (step 1). It details the cycle and records:
  - *Topology*: on the web, the authority runs on the main thread and the
    evaluator in one dedicated worker. This replaces "the authority and the
    evaluator run in a web worker" in `docs/CONCURRENCY-WASM.md` §The
    browser build. The client still holds a replica and reads only the
    applied stream (`SEED.md` §6.1). The kernel never runs on the main
    thread (§6.7), and the authority makes no kernel call.
  - *Cancellation* (the idea's option A): one small `SharedArrayBuffer`,
    apart from wasm memory, holds two counters. **commits** is bumped by
    the authority after it applies a commit and before it posts that
    commit's job, and each such job carries the count. The worker's
    `Interrupt` is answered by the poll `commits > taken`, where `taken`
    is the count of the newest commit job it has taken. Nothing is ever
    lowered, so native's raise and lower ordering has no web counterpart.
    **supersedes** is bumped for a preview, a clear and a commit, and is
    read only at feature and mesh boundaries. A preview therefore never
    stops a commit, and a running preview stops between features for
    anything newer (ADR-0019). The poll is a non-capturing function over a
    `thread_local!` handle that reads through `Atomics.load` (Arris's
    `Poll` is `Sync`), every step, or every Nth step if step 3 measures
    that one read per step costs too much.
  - *Without isolation* (`crossOriginIsolated` false, no
    `SharedArrayBuffer`): the poll answers false, a superseded evaluation
    runs to its end, previews give way at job boundaries only, and the
    status line says so once ("Evaluation can't be interrupted on this
    page: it is not cross-origin isolated").
  - *The page*: COOP `same-origin` and COEP `require-corp`. One wasm
    module, built by `cargo build --target wasm32-unknown-unknown` and
    `wasm-bindgen --target web`, loaded by both the page and the worker,
    each through its own entry point.
  - Rejected, by the idea: threads on nightly, budget slices, and
    terminating the worker.
- **`arrix-kernel`** (step 5): `Interrupt` gains a second source, a poll
  installed by the embedder (`fn() -> bool`), and a sequence form (the
  taken count). Native keeps `Arc<AtomicBool>` and its raise and lower
  unchanged. No JS in this crate.
- **`arrix-doc` session** (steps 4, 6, 7): `serve`'s request handling
  becomes a kernel-free core that is stepped one message at a time, and
  `evaluate`'s loop becomes a worker that drains its queue until idle.
  `LocalSession` is these two run on the executor's threads, with the same
  behaviour. `Job` and the worker's messages (`Publish`, `Freeze`) get a
  serde form: a snapshot as the document's serde form (ADR-0023), a frozen
  result's bodies as body bytes. These are internal messages, not the
  public protocol, so `protocol.schema.json` is unchanged. A `WebSession`
  (wasm32 only) implements `Session` on the main thread over the core,
  `postMessage` and the counters.
- **The executor** (step 7): on wasm32 it spawns the evaluator as a
  `web_sys::Worker` whose script URL the app supplies. The executor is
  still the one place a thread or worker is started, and the wasm lint's
  thread permit is unchanged.
- **New dependencies**, all wasm32-only: `wasm-bindgen`, `js-sys`,
  `web-sys` in `arrix-doc` (executor, `WebSession`) and `arrix-app` (the
  web entry, files). The layer-lint edges table gains them. They are
  pinned to the `wasm-bindgen` the CLI is installed at, and `AGENTS.md`
  §Setup names `cargo install wasm-bindgen-cli --version =<x> --locked`.
  Step 2 pinned `wasm-bindgen = "=0.2.129"`, the lock's, and installed
  the CLI at it.
- **`arrix-app`** (steps 9 to 12): a `#[wasm_bindgen]` web entry on
  eframe's `WebRunner`, plus `crates/arrix-app/web/` (`index.html`,
  `worker.js`). `Documents` holds a session that is `LocalSession`
  natively and `WebSession` on wasm32. The file flows return bytes
  asynchronously on wasm32: `<input type=file>` and files dropped on the
  page (eframe's dropped files carry bytes) for open and import, and a
  `Blob` download for save and export: an object URL on a hidden
  `<a download>`, revoked on a timer since the browser reads it
  asynchronously. They are polled each frame, and native is unchanged. `frozen_reason` says "is not available in the
  browser" for `Missing` on wasm32. Wording only: a document does not
  record its plugin's tier.
- **Scripts and gate** (steps 3, 9, 13): `scripts/web-build` (cargo,
  `wasm-bindgen`, copy `web/` into `target/web`) and `scripts/web-serve`
  (Python, a static server sending COOP and COEP). There is a native test
  harness that serves `target/web` with those headers, starts headless
  Chromium on it, and receives the page's report on a POST. The browser
  tests skip loudly without Chromium, as the visual tests skip without
  lavapipe. The harness joins `scripts/gate`, CI and `gate-selftest`'s
  lists.
- **Determinism** (step 2, `docs/CONCURRENCY-WASM.md` §Determinism): the
  same snapshot gives the same eval line on wasm32 as natively. Arris
  promises it ("same input, same output, same entity ids, on every
  platform"), but calls `f64::sin` and its kin about 150 times, and those
  are the system libm natively and Rust's libm on wasm32 (the gap
  ADR-0036 found in `gears`). The probe establishes the truth.
- No document schema change, and no `arrix-plugin-api` change (API stays
  0.8.0).

## Arris dependencies

- Cancellation: `arris_math::Control::poll`, whose poll is
  `&(dyn Fn() -> bool + Sync)`, asked at every step (arris 0.9, ask A3,
  released in 0.4.0). Nothing new is needed.
- Bit-identical results on wasm32: Arris's own promise in its README. If
  step 2 finds a difference, it is an Arris finding: a recipe under
  `crates/arrix-kernel/tests/recipes/` and a backlog line to file with
  Arris. The bit-equality half of the acceptance then waits for an Arris
  release. No libm patch or tolerance is added here. Step 2 found one
  (Findings 1), and arris 0.9 fixed it: nothing waits on Arris now.

## Acceptance

`cargo test -p arrix-app --test c4_accept` runs these through the harness
in headless Chromium on a cross-origin-isolated page:
1. `tests/docs/bracket` opens from bytes in the app. A width edit
   evaluates in the worker, and its eval line equals native `arrix eval`'s
   for the same edit, to the bit (arris 0.9, Findings 1).
2. An edit made during an evaluation stops it within 50 ms (median over
   the run's samples), and the newest generation finishes.
3. `tests/docs/standoff` opens with its Tier 2 `standoff.standoff`
   frozen, its bodies kept, and its reason shown (`debug_state()`).
   `tests/docs/north-star` opens with nothing frozen.
4. Saved as a download and re-opened natively, the document evaluates to
   native's eval line. This needs no wasm32 determinism: the saved bytes
   are the document, which native evaluates again.

Without Chromium the test skips loudly. CI runs it. The gate's existing
accepts (`c1_accept` to `c3_accept`) stay green.

## Findings

1. Step 2: wasm32 is bit-identical to native for every document without
   a gear (empty, naming, oversize-fillet, sketch-mode, standoff with its
   plugin absent). Each of the 11 with a `gears.spur` differs in the last
   place, from the first kernel call on: the gear's `extrude`, whose
   record (the profile, lines and three-point arcs) is the same bits on
   both targets, so `gears`' `libm` math holds (ADR-0036), but whose body
   is not. Arris's, recipe `gear-extrude-on-wasm32`, `docs/BACKLOG.md`.
   `wasm_determinism` requires those lines to differ, so an Arris fix
   turns it red. Acceptance 1 and 4 use the bracket, which has a gear.
   **Fixed by arris 0.9** (2026-10-22, `build(kernel): arris 0.9`): its
   transcendentals run on one `libm` on every target, so every document
   and sweep point is the same bits on wasm32. The exception, the recipe
   and the backlog line are gone, and nothing in the plan waits on Arris.
2. Step 3: the harness is a crate, `crates/arrix-web-test` (dev-only,
   native only), so the browser tests of `arrix-doc`, `arrix-plugin-host`
   and `arrix-app` share it; a test builds its page itself (`cargo build
   --target wasm32-unknown-unknown` beside the running suite, then
   `wasm-bindgen --target web`). Snap Chromium 155, headless, isolates the
   page under the harness's headers, and a module worker of the same
   module shares the counter. `Atomics.load` costs about 30 ns against a
   median Arris step of a few µs, so **the poll reads every step**
   (ADR-0042's default; the ⚠ OPEN is closed). A stop is heard at the
   first step after the bump and unwinds in about 2 ms; the rest of the
   latency is Arris's step size, and the probe's `cut_many` has a 0.2 s
   stretch without a step (`docs/BACKLOG.md`); the bracket's join stops
   in 10 ms natively, and step 8 measures it in the browser. CI's Chrome is required
   (`ARRIX_REQUIRE_BROWSER=1`, checked by `gate-selftest`) but has not run
   yet: the next push shows whether the runner image's Chrome runs the
   harness.
3. Step 6: `session/wire.rs` is the wire form: JSON, a snapshot as the
   files `save` writes (read back by `open`), blobs and bytes as base64.
   `Job::Registry` has none, since only a plugin load makes one and the
   browser has no loader (`encode_job` refuses it). `LocalSession` in a
   test can run in loopback (a thread-local, `wire::in_loopback`), every
   job and answer crossing the wire form, and `wire_tests` runs 16 of the
   session suite's scenarios that way beside a plain-versus-wired
   comparison of events and saved bytes. The scenarios using a plugin
   registry or loader stay native. The comparison hears each generation
   out before the next: two plain runs differ in what a race supersedes.
4. Step 7: `session/web.rs` holds `WebSession` (main thread) and
   `run_evaluator` (the worker's entry, which the embedder exports with
   its registry; `worker.js` keeps the messages that come while the
   module loads and hands them over). A browser worker hears messages
   only between passes, so the native `EvalWorker` gained a `drain` pass
   and its `Queue` a `Pending` read of the counters: what native learns by
   polling its channel, the web learns from `commits` and `supersedes`
   against the counts the newest job received carries. Passes run on a
   zero timer, so the jobs that came during a pass are all received
   first, which also spares an unisolated page most stale evaluations.
   **The eval line is read from the events**: a generation's `Evaluated`,
   `Assembled`, `Massed` and `Finished` are the whole `Evaluation`
   (`Evaluation::heard`), and its line equals `arrix eval`'s natively,
   plain and through the wire form (`wire_tests`). No request and no
   hook; step 14 compares that line with native's. The test page is
   `arrix-plugin-host`'s `examples/web_session`; the bracket's first
   generation and an edit evaluate and mesh in about 3 s a page,
   isolated and not.

5. Step 8: `tests/web_cancel.rs` (page: `examples/web_session/cancel.js`)
   measures the native benchmark's interval in Chromium: from a width
   edit submitted while the one before is in the gear's join, to the
   newer generation's first event: **9 ms median over 11 runs** (6 to
   14), gated at 50 ms. A preview posted in a commit leaves it to finish
   and runs behind it; a commit posted in a preview stops it (no
   `Previewed` is heard). Unisolated, the stale generation finishes and
   the newer one's first event comes about 320 ms after the edit.
6. Checkpoint (2026-10-16), the revision of steps 9 to 14:
   - The committed `tests/docs/north-star` has no `fasteners` feature,
     since C3's accept places them at run time. `robotics` is an exporter
     and one of the app's Tier 0 plugins, so the north star opens in the
     browser with nothing frozen. Acceptance 3 moves to
     `tests/docs/standoff`, whose Tier 2 feature has committed bodies.
   - Acceptance 1 is plain bit equality since arris 0.9 (Findings 1).
     Acceptance 4 never depended on it.
   - The harness takes one POST and has no DevTools protocol, so the page
     drives the app through its handle's exports, not through egui clicks.
     Files come in through `DataTransfer`, and downloads are caught by a
     wrapped click.
   - CI hasn't run the browser harness yet, because `main` is 11 commits
     ahead of `origin`. A push before step 9 shows whether the runner's
     Chrome runs it (Findings 2).

7. Step 9: `src/web.rs` holds the web entry (`WebHandle`, `run_evaluator`)
   and `web/` the page. The app starts on an empty start (no document:
   opening one needs step 10's `WebSession`) and draws in about 3 s,
   isolated, debug build. **The renderer is both of wgpu's web backends**,
   eframe's default: WebGPU where the browser gives an adapter, else
   WebGL2. Headless Chromium 155 here has `navigator.gpu` but no adapter,
   with `--disable-gpu` and with `--enable-unsafe-webgpu`, so the page
   lands on WebGL2 (`backend()` is `Gl`), and every viewport pipeline is
   made there (a screenshot shows the background drawn). A desktop browser
   with WebGPU wasn't tried here. `arrix-viewport`'s `webgl2_shaders`
   translates every shader to GLSL ES 3.0 through `naga` 30. The debug
   module is 31 MB and the release one (`scripts/web-build --release`)
   23 MB, uncompressed.
8. Step 10: the app holds a `DocSession`, `LocalSession` or `WebSession`
   by target, and keeps each tab's newest finished line from its events
   (`heard_line.rs`, both targets). The parameter edit goes through
   `ArrixApp::submit` as one gesture, since the app has no parameter
   form: the property form edits a feature, and `arrix eval --sweep w=…`
   sets the document parameter. The page's lines for the bracket and its
   width at 80 mm (the sweep's last point) **equal the goldens to the
   bit**, isolated and not, so the browser tests already hold acceptance
   1. A line goes from the page as the text the app wrote, since
   `JSON.parse` makes `20.0` an integer. Each tab starts a worker of its
   own.
