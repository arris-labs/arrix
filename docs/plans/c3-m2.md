# Plan: c3-m2

- Started: 2026-10-13
- Cycle: C3, M2 (a plugin reads an assembly); ADR-0034 details the cycle
- Idea: none. Verbatim from the human: "/plan c3-m2". The scope is
  ADR-0034 §Decision 2 and `docs/ROADMAP.md` §C3's in-list.

## Goal

A plugin can read an evaluated document and write a file from it, on all
three tiers. The world gains a `document` import, the snapshot read, which
gives parts, their final bodies' meshes, assemblies with solved poses and
joints, and mass and inertia. It also gains an `exchange` export: an
exporter takes a snapshot and options and returns files. `arrix export
--exporter <id>`, `arrix describe`, `arrix test`, `arrix serve` and the
Python SDK all reach exporters. `robotics`, first-party plugin #1, is a Rust
crate on `arrix-plugin-api` alone. It runs at Tier 0 or as a Tier 1
component and exports an assembly as URDF: a link per component, joints
with their limits, STL meshes, and inertials from the document's materials.
Its output is the same to the byte at Tier 0 and Tier 1. Two independent
readers, urdfdom and a Python URDF loader, read the links, joints, limits,
masses and link poses at two joint values the way ArriX solves them.

## Non-goals

- The `commands` export, `fasteners`, out-of-tree workspaces,
  `arrix-plugin-test` and the API's stability review: M3 (ADR-0034).
- Importers, analyses, plugin document data, panels and viewport drawables
  by plugins (`docs/ROADMAP.md` §C3, out). Robotics settings with no home
  in the core, such as a joint's effort and velocity, are the exporter's
  options (ADR-0034, Consequences).
- SDF and MJCF; ROS `package://` paths beyond a prefix option; a
  collision geometry other than the visual mesh.
- A feature reading the snapshot: `evaluate` keeps `kernel` and its
  resolved inputs only (`docs/PLUGINS.md` §Capabilities), and a `document`
  call made during it is `plugin.capability`.
- A body's B-rep bytes in the snapshot (Arris ask A2). The snapshot holds
  meshes, which are enough for URDF.
- The app's export dialog listing plugin exporters, unless the human decides
  otherwise (Open question 2).
- Tier 1 in the browser (C4's ADR).

## Design deltas

- **ADR-0037, the snapshot read and exporters** (step 2), from step 1's
  probe:
  - *The world's shape.* Either one world whose every export a plugin
    implements, with the SDK supplying empty ones (`describe` returning no
    feature types, no exporters), or several worlds with the host reading
    which exports a component has. Step 1 found both work. A guest built for
    a smaller world gives a component with that world's exports only, which
    one host bound to the whole world loads interface by interface (the
    world's own bindings refuse it). An import the guest never calls is
    absent from the component.
  - *The `document` interface* (read-only, under `document-read`): plain
    records, SI, Z-up, every id `arrix-core`'s. It gives the parts (id,
    name, final bodies by `<feature>.<slot>`, each body's refined mesh in
    the part's frame as `f32` positions and normals and `u32` triangles,
    and its material's name and colour), each part's mass, centroid and
    inertia about the centroid (`arrix_doc::Inertial`, or the `mass.*`
    diagnostic), and the assemblies. An assembly's components are listed
    at every depth by path, with the part each is of and its solved pose
    in the assembly's frame. Its joints carry kind, parent and child paths,
    anchor frames in each one's component frame, axis, limits in SI, value,
    and status. Calls are by function, so a plugin fetches only the meshes
    it writes (step 1 measures a large mesh across both boundaries).
  - *When it may be called*: only during an `exchange` call, against the
    generation that call was made on. A call outside one, a call during
    `evaluate`, or a call by a plugin without `document-read` is
    `plugin.capability`. At Tier 1, a component that imports `document`
    without the capability is refused at load: step 1 found that an import
    a guest never calls is not in its component.
  - *The `exchange` export*: `exporters() -> list<exporter-spec>` (id
    `<plugin>.<name>`, title, the extension of its main file, its subject,
    which is a part or an assembly, and `params` and `choices` reusing the
    feature form's specs, so a form is derived as for a feature).
    `export(id, subject, params, choices) -> result<list<file>, diagnostic>`,
    where `file { name, bytes }` and `name` is a relative path, `/`
    separated, with no `..` and no absolute part, refused otherwise as
    `export.path`. The first file is the main one. The host writes them,
    and a plugin never sees a path (`docs/PLUGINS.md` §4).
  - *Determinism*: an export is a pure function of the snapshot and its
    options. It runs in a fresh store at Tier 1 and is checked twice by
    the test kit. Its math is `arrix_plugin_api::math` (ADR-0036).
  - *The session*: `Request::Export` takes an exporter id beside today's
    `format`, plus the options. `Exported` carries the files. The protocol
    schema's version is bumped.
- **`arrix-plugin-api`** (step 3): the `document` import and the
  `exchange` export in the WIT, and their Rust mirror. The mirror is a
  `Snapshot` trait (the import, as `Kernel` is), an `Exporter` trait (the
  export, as `Feature` is), and plain types. `export_plugin!` grows to
  take a plugin's features and exporters, in the shape the ADR picks.
  API: breaking, 0.6.0 → 0.7.0 (a grown world changes what a component
  must provide). Every first-party manifest's `api` range follows, as do
  the wire's generated codec, the Python SDK, and `wit_equality.rs`'s
  inventory.
- **`arrix-doc`** (step 4): `Registry` holds exporters beside feature
  types (an `ExporterType` trait, as `FeatureType`). The snapshot is built
  from an `Evaluation`, its meshes refined, its masses from the mass pass,
  and its assemblies from `AssemblyOutcome` and the document's joints.
  `Evaluator::export_with` is added. Nothing persists, so the schema does
  not change.
- **`arrix-plugin-host`** (steps 4, 6, 7): `register_tier0` registers
  exporters. Tier 1 serves `document` from a table of the call's snapshot
  and calls `exchange` in a fresh store, with fuel. The Tier 2 wire gains
  `exchange.*` (host to plugin) and `document.*` (plugin to host, while
  an export runs), generated from the WIT. `document-read` is enforced at
  the wire as `kernel` is.
- **Test kit** (step 5, `docs/PLUGINS.md` §The test kit): a plugin's
  `[test]` table may name `exports`, each a fixture document, an exporter,
  a subject and options. Each is run twice to identical files (the
  determinism check), and the check names the files and their hashes.
- **CLI** (step 5): `arrix export <doc> --exporter <id> [--assembly <a> |
  --part <p>] [--option <name>=<expr>]… -o <path>`. One file is written to
  `<path>`. Several go into the directory `<path>`, created if missing, and
  not overwritten where a file of the same name exists unless `--force` is
  given. `describe` lists exporters with their options.
- **`plugins/robotics`** (steps 8, 9): Tier 0 and `guest`, holding
  `robotics.urdf` on an assembly. It writes a `base_link` that every
  grounded component hangs from by a fixed joint, a link per component at
  every depth (named by its path's names), a joint per assembly joint
  (`revolute` with limits, `continuous` without, `prismatic` with limits,
  `fixed`), the joint origin in the parent link's frame from the anchors,
  and `<axis>`. A component with neither joint nor pose hangs from
  `base_link` at its solved pose, by a fixed joint, with a warning in the
  URDF's comment. Each link gets one binary STL per part, in metres, shared
  by the components of that part, plus `<inertial>` from the part's mass
  outcome; a part with no mass gets no inertial, with a warning. Its options are
  `effort`, `velocity` and `mesh-prefix`. Roll, pitch and yaw come from the
  rotation through `math::atan2`, as `clippy.toml` holds it.
- No schema change: a document does not record exporters.

## Arris dependencies

None new. Refined meshes are the evaluator's (`MeshDetail::Refined`,
`arrix-kernel`'s tessellation on the pinned `arris` 0.8). Volume,
centroid and inertia come from the mass pass (ADR-0031). The plugin writes
STL itself from the mesh, since a plugin names no Arris type, and no
kernel call is made during an export.

## Steps

Complexity: **[1]** routine — the design says what to write, the tests are
mechanical; **[2]** careful — a case to get right within a given design;
**[3]** unproven — behaviour that has to be established here.

- [x] **[3]** Step 1 — probe the grown world at Tier 1 and Tier 2: a probe
  test in `arrix-plugin-host` (as `probe_tier1.rs`) on a scratch WIT with
  a `document` import and an `exchange` export beside `feature`.

  `feature` only, or only `exchange`, against that world; whether an

## Open questions

- RESOLVED 1 (human, ADR-0037 §10, registered as ids): the core's STEP, STL and OBJ as exporters `core.step`,
  `core.stl` and `core.obj` in the registry, listed by `describe` and
  reachable by `--exporter`, with `--format` kept as their shorthand.
  `docs/PLUGINS.md` §4 already says the core STEP exporter goes "through
  this same surface". The alternative is to correct that line and keep
  the core formats apart. The recommendation is to register them as ids
  that are implemented natively, since STEP needs the B-rep, which the
  snapshot does not carry. Human, by step 2.
- RESOLVED 2 (agent, step 5, a backlog line; add it to `docs/BACKLOG.md` at retirement): the app's export dialog listing plugin exporters with their
  option form in M2, or a backlog line. The recommendation is the backlog:
  C3's in-app accept is the fastener command, and the session request
  already lets the app add the dialog later at no protocol cost. Human, by
  step 5.
- RESOLVED 3 (human, ADR-0037 §8, a directory): several files are written as a directory (recommended:
  URDF readers resolve meshes relative to the file) or as a zip. Human,
  by step 2.
- RESOLVED 4 (agent, ADR-0037 §4, fixed chord 1e-4): the snapshot's meshes at refined detail (`MeshDetail::Refined`, 1e-4 of the diagonal, see the ADR's erratum;
  recommended, as STL export uses) or with a detail the exporter asks
  for. Agent, from step 1's sizes, in step 2.

## Findings

- Step 5: the session protocol stays at version 1. `Request::Export`'s
  `exporter` and `Exported`'s `files` are optional and defaulted, which
  ADR-0026 §3 calls additive; ADR-0037 §11's "bumped" is read as the
  schema golden. No plugin reaches the binary with an exporter before
  steps 6 to 8, so step 5's tests hold the writing and flags in unit tests
  and `tests/export_exporter.rs` (core ids, refusals, `describe`), the
  session path in `plugin-host/tests/snapshot.rs`, and the `[test] exports`
  check runs for the first time on `robotics` (step 9).
