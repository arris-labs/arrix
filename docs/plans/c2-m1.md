# Plan: c2-m1

- Started: 2026-10-11
- Cycle: C2, M1 (assemblies in the document, headless); ADR-0027 splits
  the cycle
- Idea: c2-mechanical-core (absorbed: option B; decisions
  1, 3, 4 and 5 taken as recommended, 2 as the human decided it
  2026-10-11; step 1 deletes the file)

## Goal

A document holds assemblies: components that place a part or a nested
assembly, grounded by a pose or placed by one fixed, revolute or prismatic
joint whose value, limits and offset are expressions, and solved by tree
forward kinematics in the evaluator, off the UI thread. A vendor part comes
in through `core.import-step`, the file kept as a blob in the document and
its faces named from the file's entities. The scenario runs headless: a
revolute joint anchored to a face of an imported STEP part and to a face
downstream of a frozen plugin feature follows an upstream width edit, live
and with the plugin removed; a deleted anchor face is `ref.lost` with
candidates on the joint; the document saves and reopens byte-identical, and
a schema-3 document migrates. `arrix eval` and `arrix serve` carry it. The
risk retired: a persistent name across parts and instances, into imported
and frozen geometry.

## Non-goals

- The app (instanced meshes, picking by component path, the assembly tree,
  the joint form and tool, the drag and its preview): M2.
- STEP with product structure both ways, materials, mass properties, the
  cycle's accept against Open CASCADE: M3. STEP export stays refused
  (`kernel.export.unit`) until Arris ships A12.
- Measure, section view, 3MF, DXF/SVG sketch exchange: the named cycle
  "the mechanical core completed" (ADR-0027).
- A general mate solver or closed loops (named cycle): a second joint onto
  a placed component is `assembly.loop`, never solved.
- In-context design: a feature naming another part's geometry stays
  `input.cross-part`; joint anchors are the only cross-part references.
- References to other `.arrx` files; one import feature reading several
  solids or a product tree (M3 maps a product tree to parts and an
  assembly); a cache of one file read across several import features
  (backlog, when a budget asks).
- Healing or repairing a vendor file: a refused solid is a diagnostic and
  an Arris fixture.
- `arrix-plugin-api`: no change. The Python SDK: no new helpers (the
  commands cross as JSON already).

## Design deltas

- **ADR-0027, C2 split.** C2 is "assemblies and exchange": the exchange
  unit, `core.import-step`, assemblies, materials and mass properties, STEP
  with product structure (A4); milestones M1 (this plan), M2 (the app), M3
  (exchange, mass, the accept). Measure, section view, 3MF and DXF/SVG move
  to a named cycle, "the mechanical core completed", scheduled once Arris
  releases its query cycle (A6). Amends `SEED.md` §7's C2 line and its
  named list; rewrites `docs/ROADMAP.md` §C2 with the milestones.
- **ADR-0028, the exchange unit.** Each side keeps its convention: Arris
  unit-agnostic, ArriX SI. STEP is read with `length_unit: Metre` passed
  explicitly, and written in the model's metres declared as metres once
  Arris's writer takes a unit (A12); until then `export_step` is refused as
  `kernel.export.unit`, the call recorded. A "write in mm" option waits for
  a reader that needs it.
- **ADR-0029, assemblies in the document.**
  - *Model* (`arrix-doc`): `Document.assemblies: BTreeMap<AssemblyId,
    Assembly>`; `Assembly { id, name, components, joints }`; `Component {
    id, name, of: Part(PartId) | Assembly(AssemblyId), pose: Option<Pose> }`
    (a pose grounds it); `Joint { id, name, kind: Fixed | Revolute |
    Prismatic, parent: Anchor, child: Anchor, value: Expr, offset: Expr,
    limits: Option<[Expr; 2]>, flip: bool }`; `Anchor { path:
    Vec<ComponentId>, axis: PersistentName, origin: Option<PersistentName>
    }`, the path from the joint's assembly down to a part. `Pose` is a
    position (three lengths) and URDF's fixed-axis roll, pitch, yaw (three
    angles), all expressions. New ids `AssemblyId`, `ComponentId`,
    `JointId`.
  - *A version across parts* is the part's final state, as its own
    evaluation leaves it (rollback honoured): an anchor's input hash is the
    hash of the last evaluated feature of each slot it names. This closes
    the "until assemblies say" of `docs/DATA-MODEL.md` §Bodies across
    features for anchors only; features keep `input.cross-part`.
  - *An anchor's frame*: the axis entity gives z and a point (a
    cylindrical face's axis, a circular edge's centre and normal, a
    straight edge's line, a planar face's normal at its frame origin); an
    origin face moves the point to where the axis meets its plane. x is the
    origin face's u projected, else the world axis least aligned with z
    (X before Y before Z) projected, so it is deterministic. `flip` turns
    the child's frame half a turn about its x.
  - *FK*: grounded components at their pose; a joint places its child at
    `parent_world · F_parent · motion(value + offset) · F_child⁻¹`, motion
    a rotation about z (revolute), a translation along z (prismatic) or
    none (fixed). A forest only: a component with a pose and a joint, or two
    joints, is `assembly.loop` on the later joint (by id), which is then
    ignored; a component with neither is `assembly.unplaced`, placed at
    identity. A value outside its limits is `assembly.limit`, applied
    as given. Nested assemblies compose their solved poses. All pure math in
    `arrix-doc`; the frames are recorded kernel calls.
  - *Deferred to M2's ADR*: whether a joint drag's preview solves FK
    client-side like a sketch drag (no kernel call is involved).
- **Persistent naming**: `NameRoot::Imported { feature, entity: u64,
  instance: u32 }` from Arris's `Role::File(FileEntity)`; text
  `import.<ID>.<entity>[.<instance>]`, instance 0 not written and an error
  when written, as ADR-0011's index. Stable for one file; a vendor's next
  revision can lose a name, which is `ref.lost`, never a re-bind. Several
  entities of one kind from one file entity (an edge split at a pole):
  piece `k > 0` adds `mod.<ID>.<k>` (found in step 5).
- **`core.import-step`** (`docs/DATA-MODEL.md` §The core feature types): no
  inputs, a `solid` count param (which solid of the file, from 1 in the
  reader's order, default 1), one output slot `body`; the file is the
  record's `file`. A refused solid is `kernel.import.<refusal-kind>`
  naming the file entity; no file is `import.no-file`; a `solid` past the
  file's count is `import.no-solid`. Built-in, so never frozen.
- **Schema 4** (`docs/DATA-MODEL.md` §File format): `FeatureRecord.file:
  Option<ImportedFile { name, blob }>` (the file's base name for display,
  never a path) and `assemblies/<assembly-id>.json`; the zip reader admits
  `assemblies/`. A blob a record's `file` names is kept on save. 3 → 4 is
  the identity bar the header, fixture `tests/docs/migrations/schema-3/`
  (a copy of `tests/docs/slice/`).
- **Commands** (`docs/DATA-MODEL.md` §Commands and undo): `AddFile { bytes
  }` (named by its BLAKE3, inverse `RemoveFile`, refused while a record
  names it), `AddAssembly`/`DeleteAssembly`, `AddComponent`/`EditComponent`/
  `DeleteComponent`, `AddJoint`/`EditJoint`/`DeleteJoint`, each with its
  inverse. An import is one gesture, a `Group` of `AddFile`, `AddPart` and
  `AddFeature`. A component of a deleted part or a joint of a deleted
  component is refused (`assembly.dangling`), not cascaded.
- **The DAG**: assembly, component and joint nodes. A joint reads its
  anchors' parts (their final features, as above) and its expressions'
  parameters; a component reads its part or assembly; an assembly
  containing itself, at any depth, is `dag.cycle`.
- **Evaluation**: after the parts, each assembly in id order, nested ones
  first; an `AssemblyOutcome { components: world poses by path, joints:
  outcome each }` cached by its input hashes.
- **`arrix-kernel`**: `import_step(feature, file, solid)` (`KernelOp::
  ImportStep { feature, file: blake3, solid }`, a fixture recipe carrying
  the file's bytes) and `anchor_frame(body, axis, origin)` (`KernelOp::
  AnchorFrame`), both recorded. New codes `kernel.import.<kind>`.
- **Surfaces** (ADR-0026, additive, no version bump): the eval line gains
  `assemblies`; the protocol gains the commands and a
  `SessionEvent::Assembled { generation, assembly, outcome }`; schema
  goldens refreshed, each commit body saying `Harness: … additive`.

## Acceptance

`cargo test -p arrix-cli --test c2_m1`, on `tests/docs/assembly/`: a
bracket part (the slice's gear joined, then a bore cut downstream of it)
grounded, a servo part imported from `tests/fixtures/step/`, and a revolute
joint from the servo's shaft face to the bracket's bore face, its value a
parameter.

- The servo's world pose matches a hand-computed one; setting the joint's
  parameter rotates it about the bore's axis.
- Editing the bracket's width moves the bore, and the servo with it.
- `arrix eval --without-plugin <gear>` gives the same poses, the gear
  frozen and saying why.
- Deleting the bore's cut leaves the joint `ref.lost` with candidates, the
  servo `assembly.unplaced`, and every other result standing.
- Save, open, save gives the same bytes, directory and `.arrx` both; the
  schema-3 fixture migrates to the slice's bytes.
- `arrix serve --stdio` on the document announces the same outcome as an
  `Assembled` event.
- The whole gate (`.githooks/pre-commit`, `.githooks/pre-push`) stays
  green, the wasm build included.

## Open questions

None open. Found in step 5:

- The reader makes several entities of one kind from one file entity
  (Arris splits an edge where it runs through a pole; a rebuilt seam or
  degenerate edge takes its face's entity): the first keeps the name,
  piece `k` adds `mod.<feature>.<k>` (`tests/fixtures/step/half-ball.stp`,
  copied from Arris's corpus).
- Arris's recipe `step` op reads in millimetres and takes no unit, so a
  recipe holding an import is written in millimetres, every length and
  the precision times 1000, rather than asking Arris for a unit field.
- The servo fixture is Arris's own STEP of a recipe in the probe (no
  vendor tool on this machine); M3's accept reads a real vendor file.

Found in step 6:

- ADR-0029 §3 leaves the point along a cylindrical face's axis and a
  straight edge's line open: it is the face's lowest extent along z and
  the edge's start, so it follows the geometry and not how it was made;
  z is the surface's or curve's own orientation, as `edge_axis` already
  took it (`flip` is the joint's answer to a mate the wrong way round).
- No real file has needed a B-spline cylinder as an axis yet, so no Arris
  line: the refusal names the face (Open CASCADE's
  `tests/fixtures/step/nurbs-cylinder.step`, copied from Arris's corpus).

Found in step 9:

- `core.import-step` has no create command until M2: a generic "New
  import step" would make a record with no file (`import.no-file`) and
  move the app's ribbon and palette goldens for a command that cannot
  finish. `Registry::creatable_specs` leaves the types that read a file
  out of the command registry and the configuration, so `describe` and
  `docs/CONFIG-CATALOG.md` are unchanged here; M2's import command lists
  it. The evaluator reaches a file through the core-only `FileKernel`
  (`FeatureType::evaluate_file`), not the plugin API's `Kernel`.

Found in step 11:

- A pose in an outcome is a `Frame` (where the component's origin and
  axes land), so it crosses as plain data with no new type. A fixed
  joint's value, offset and limits are not read (its value is 0). Anchor
  frames are cached apart from the assembly's outcome, by the body's
  version and the names, so a new joint value calls no kernel.

Decided at planning by the agent, as the human asked (2026-10-11):

- The idea's decisions 1, 3, 4 and 5 as recommended: split C2 (ADR-0027);
  assemblies inside one document; no in-context design in C2; M3's accept
  reads the export with Open CASCADE through a script, never in CI, into a
  committed text golden, on an assembly ArriX builds (bracket, servo,
  horn) and one vendor STEP Arris reads cleanly.
- This is one plan per milestone, as the boundary cycle was; M2 and M3
  are planned when M1 retires.
- An import feature reads one solid into one `body` slot; a multi-solid
  or structured file is several features, then M3's product-tree import.
- The anchor-frame conventions, URDF's roll-pitch-yaw for a pose, and
  loops and missing placements as diagnostics rather than refusals
  (fail soft, the document can hold them mid-edit), all recorded in
  ADR-0029.
